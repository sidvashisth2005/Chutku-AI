Precise technical assessment
MARK LIV is a local automation framework with a Gemini Live voice interface. It has four distinct layers:
Interaction layer
PyQt GUI · microphone · speakers · keyboard input · phone dashboard

Reasoning layer
Gemini Live session · system prompt · transcripts · function calling

Execution layer
Built-in actions · inline tools · plugins · confirmation/undo gates

Persistence layer
Configuration JSON · long-term memory JSON · browser profiles · certificates
The core principle is:
Gemini decides what structured action should happen; Python performs it using local libraries, operating-system APIs, subprocesses, browser automation, or separate Gemini requests.

1. Exact runtime sequence
Startup
[main.py (line 2269)](D:/Project/Mark-LIV-main/main.py:2269) performs the following:
1. Creates the PyQt interface.
2. Shows the setup overlay if an API key has not been configured.
3. Starts a background thread.
4. Constructs JarvisLive.
5. Auto-discovers actions from actions/*.py.
6. Auto-discovers plugins from plugins/*.py.
7. Starts an asyncio event loop.
8. Starts the local phone dashboard.
9. Connects to models/gemini-3.1-flash-live-preview.
10. Starts concurrent audio, playback, monitoring, dashboard, and reconnect tasks.
The main Gemini connection is configured in [_build_config() (line 952)](D:/Project/Mark-LIV-main/main.py:952).
It gives Gemini:
- A dynamically rendered system prompt
- Current date and time
- Assistant and user names
- A subset of long-term memory
- The precise list of tools discovered at runtime
- Tool parameter schemas
- Voice configuration
- Input and output transcription
- Conversation resumption
- Sliding-window context compression
- Optional proactive audio and speech-detection tuning
Voice request lifecycle
Microphone
  ↓ 16 kHz, mono, signed 16-bit PCM
sounddevice callback
  ↓
wake/PTT/echo/mute gates
  ↓
asyncio audio queue
  ↓
Gemini Live send_realtime_input()
  ↓
Gemini detects speech and interprets request
  ↓
Gemini either answers or emits function_call
  ↓
_execute_tool()
  ↓
Local action executes
  ↓
FunctionResponse returned to Gemini
  ↓
Gemini generates a natural spoken answer
  ↓ 24 kHz PCM
speaker queue → sounddevice output
The microphone path is implemented in [_listen_audio() (line 1296)](D:/Project/Mark-LIV-main/main.py:1296), while responses and function calls are handled in [_receive_audio() (line 1459)](D:/Project/Mark-LIV-main/main.py:1459).
Text commands
Typed commands bypass microphone capture and are sent into the same Gemini session as a completed user turn. They therefore have the same memory, tools, and conversation context as spoken requests.
Session continuity
Gemini periodically sends a resumption handle. MARK LIV retains the newest valid handle in memory and supplies it during reconnection.
It can survive:
- Temporary network failure
- Audio-device changes
- Most unexpected Live API disconnects
It deliberately does not persist the handle to disk. Closing and reopening MARK LIV begins a new Gemini conversation, although long-term JSON memory remains.
2. What it can actually do
Real-time conversation
It can:
- Listen continuously while awake
- Detect when the user finishes speaking
- Answer with native Gemini audio
- Transcribe both sides
- Maintain conversation context during the running session
- Switch among configured Gemini voices
- Speak in the language of the most recent message
- Accept voice, typed, or phone-microphone input
- Reconnect without immediately losing the conversation
- Generate lip movements from audio and transcript data
Limits:
- It requires internet access for Gemini.
- It is not an offline conversational assistant.
- Voice interruption while it is speaking is explicitly disabled.
- It does not perform reliable speaker identification.
- It cannot distinguish every person in a room.
- Audio context disappears when the program is restarted.
- Push-to-talk outside Windows may only work while the app has focus.
Wake word and microphone privacy
The optional wake-word subsystem is local.
When wake-word mode is asleep:
- Microphone frames are not sent to Gemini.
- Frames are passed to a local openwakeword detector.
- Detection wakes the main assistant.
- It returns to sleep after 120 seconds without user speech.
Push-to-talk requires Ctrl+Space. When enabled, microphone frames are not streamed unless the key is held.
The echo guard compares recent speaker output with microphone energy after playback. It reduces the chance that MARK LIV hears its own last response and answers itself.
Limits:
- The echo guard is heuristic, not acoustic echo cancellation comparable to conferencing software.
- Voice barge-in is disabled.
- Wake-word reliability depends on microphone quality, noise, and the optional model installation.
Screen and camera vision
The screen_process tool can:
- Capture the current primary display using mss
- Capture a webcam frame using OpenCV
- Resize/compress the frame
- Inject the image into the active Gemini Live conversation
- Display a local camera preview
- Ask Gemini a question about that frame
It labels frames as either:
- SCREEN CAPTURE
- WEBCAM
Limits:
- Vision is snapshot-based.
- It does not continuously watch the screen.
- It cannot notice changes that occur after capture.
- The tool has a four-second duplicate-call cooldown.
- Camera access is effectively single-frame analysis plus local preview.
- OCR quality is limited by screenshot resolution and Gemini’s interpretation.
- Multi-monitor selection is not exposed in the tool schema.

Alerts have a five-minute cooldown.

Topic monitoring
It stores user-selected topics in memory and performs at most one DuckDuckGo news check per topic per day. It compares only the top headline’s hash with the previous one.
It explicitly blocks many crypto-related terms.
This is not real-time monitoring. It is a daily top-headline comparison.
Proactive messages
After 15 minutes without user speech, and at least 20 minutes after the previous proactive message, it may send Gemini a contextual check-in prompt.
The prompt can use:
- Time of day
- Stored memory
- Monitored topics
- Recent conversation turns
The proactive turn is instructed not to call tools.
3. Persistence and memory
Memory is a structured JSON document, not a vector database.
Categories are:
identity
preferences
projects
relationships
wishes
notes
sessions
monitors
Each regular entry contains a value and update timestamp.
At connection time:
- Up to roughly 900 characters of important memory are injected.
- A short index of additional keys is included.
- Missing details can be searched with recall_memory.
Recall uses keyword/token scoring. It does not perform embeddings or semantic nearest-neighbor search.
Storage has a 200,000-character runaway guard. Session summaries are capped at three recent entries and consumed by briefings.
Limits:
- No encryption at rest
- No database transactions
- No semantic memory
- No provenance or confidence score
- Gemini decides what is “worth remembering”
- A mistaken memory remains until manually removed
- Memory is shared by anyone using the same OS account

The model ladder is:
FAST:
Live → gemini-2.5-flash-lite → gemini-2.5-flash

SMART:
Live → gemini-2.5-flash → gemini-2.5-flash-lite

SEARCH:
gemini-2.5-flash → gemini-flash-latest → gemini-2.5-flash-lite
At most three one-shot Live sessions may run concurrently. A model returning quota errors is skipped for five minutes.
6. Hard boundaries
MARK LIV cannot reliably:
- Work conversationally without an internet connection
- See the screen continuously
- Control another computer unless the software is running there
- Operate arbitrary smart-home devices without a plugin
- Guarantee a message reached the intended person
- Bypass CAPTCHA, MFA, secure desktops, or OS privilege prompts
- Book flights, make purchases, or perform banking safely
- Reliably automate any arbitrary UI
- Remember full past conversations across restarts
- Restore every file or setting it changes
- Analyze complete huge documents or datasets
- Run generated code safely
- Replace formal calendar, email, or messaging APIs
- Prove that a browser operation succeeded merely because a click was simulated
The current checkout also has no installed functional plugins—only [plugins/_template.py](D:/Project/Mark-LIV-main/plugins/_template.py).

- Encapsulate provider-specific code behind interfaces so the application can

- Use asyncio for orchestration, but never perform blocking filesystem,
  subprocess, model, image, or browser work on the event loop.
- The sounddevice callback must do bounded constant-time work only.
- Use bounded queues and define an explicit overflow policy for every stream.
- All long-running tasks must support cancellation and deterministic shutdown.
- Do not use global mutable state where a scoped service can be injected.
- Keep modules focused. No main.py or UI module should become a monolith.
- Use type hints throughout.
- Use dataclasses or Pydantic models for events, tool calls, results,
  configuration, memories, permissions, and dashboard messages.
- Store secrets through an operating-system credential backend when available;
  provide a clearly documented local fallback.
- Never log API keys, bearer tokens, private message bodies, microphone audio,
  or raw credential files.
- Add structured logging with secret redaction.
- Add pytest tests as each subsystem is implemented.
- Run tests and static checks after every milestone.
- If a dependency or API is unavailable, preserve the source, implement a fake
  adapter, and document what remains unverified. Do not fake successful tests.

LIVE SESSION

Implement a LiveSession service that:

- Connects using a provider adapter.
- Sends 16 kHz mono signed 16-bit PCM input.
- Receives model-native audio and plays it at the required sample rate.
- Receives input and output transcription.
- Processes function calls.
- Returns structured function responses.
- Captures only valid resumable session handles.
- Reconnects with exponential backoff.
- Rejects an invalid resumption handle once and then starts clean.
- Preserves conversation state across ordinary reconnects.
- Rebuilds the session when voice or audio configuration changes.
- Uses sliding-window context compression if supported.
- Falls back cleanly when preview-only configuration fields are rejected.
- Has a fully deterministic FakeLiveSession for tests.

AUDIO

Implement:

- Microphone enumeration and persistent device selection.
- Speaker enumeration and persistent device selection.
- Fallback to the system default if a saved device disappears.
- 16 kHz microphone streaming.
- Provider-required output-rate playback.
- Bounded microphone and playback queues.
- Push-to-talk using Ctrl+Space.
- Optional local wake-word detection.
- A sleep state in which microphone frames are never transmitted.
- Echo-tail suppression based on recent output audio and measured output latency.
- Fast interruption through explicit UI controls.

SAFETY

Implement policy in code, not only in the system prompt.

Risk categories:

- READ_ONLY
- LOCAL_REVERSIBLE
- LOCAL_DESTRUCTIVE
- EXTERNAL_COMMUNICATION
- ACCOUNT_OR_PURCHASE
- POWER_OR_CONNECTIVITY
- CODE_EXECUTION

Require UI-issued confirmation for:

- shutdown
- restart
- Wi-Fi disable
- sending messages
- deleting anything not recoverably moved to Trash
- purchases or submissions
- external uploads
- installation of dependencies
- executing newly generated or untrusted code
- scheduling shutdown
- opening firewall ports
- actions involving credentials

The language model must not be able to supply or forge confirmation. A confirmed
action must be tied to an immutable hash of its previewed arguments and must
expire.

Maintain an audit log describing who requested an action, what arguments were
previewed, whether it was confirmed, what executed, and whether success was
verified. Redact secrets.

Maintain an undo stack for reversible operations. Each undo entry stores a
description, timestamp, reverse callable or durable reverse specification, and
precondition checks. Never restore over a path that has changed without asking.

DELIVERY PROCESS

Work in milestones. At the beginning:

1. Inspect the repository.
2. Write ARCHITECTURE.md.
3. Write a milestone checklist.
4. Establish formatting, linting, typing, and pytest.
5. Implement the smallest complete voice/text-to-tool-to-result vertical slice.

After each milestone:

1. Run formatters.
2. Run lint/type checks.
3. Run relevant tests.
4. Report files changed.
5. Report verified behavior.
6. Report limitations and unverified hardware behavior.
7. Continue unless blocked by missing credentials, unavailable hardware, or a
   decision that materially changes product behavior.

Do not call the application complete merely because the UI launches. Completion
requires:
- tested session lifecycle
- tested tool dispatch
- tested confirmation boundary
- tested memory
- tested reconnect behavior
- tested path security
- documented setup
- documented privacy behavior
- documented platform capability matrix
- a reproducible package/build procedure

Start by producing ARCHITECTURE.md and the implementation roadmap, then build
the first tested vertical slice.
That master prompt recreates the product’s intent while fixing its largest technical weaknesses: monolithic modules, UI-driven automation without verification, insufficient hard confirmation coverage, unsandboxed generated code, and LAN dashboard security.
